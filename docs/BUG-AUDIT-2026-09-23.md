# Module bug audit — 2026-09-23

Scope: the core framework (Module, EventManager, Config, BlinkManager, LagManager,
MixinNetworkManager) + the recently changed modules (Panic, FakeLag, Blink, KillAura,
BlockHit, LagRange, AutoBlockIn, PlainAura, TargetFilter, AntiVoid),
plus a script pass over all 143 modules for two kinds of problem:
"an event handler that does not check `isEnabled()`" and "a setting declared but never used".

**Not read line by line:** HitCheck, FlagDetector, Adaptive, ServerFingerprint,
AutoTune, KnockbackDelay, the render modules.

## Background: why "no isEnabled check" is a whole class of bug

`Myau.java` calls `EventManager.register(module)` for **every** module at start-up,
switched on or not. So every `@EventTarget` is called all the time, and a module must
check `isEnabled()` itself. Where it does not, the module works even while "off".

## 🔴 Critical

### 1. ✅ Blink's gradual release never actually released anything
`Blink.drain()` → `PacketUtil.sendPacketNoEvent()` → `sendPacket(p, null)`
(the varargs overload, SRG `func_179288_a`) → `MixinNetworkManager.sendPacket2`
→ `blinking == true` at that moment → `BlinkManager.offerPacket()` takes the packet back into the end of the queue.

- The queue never got shorter, it was only "rotated" (its order scrambled).
- With no C03 in the queue, `while (allowance > 0)` never ended → **the client froze**.
- A release really ended only when `release-on-correction` received an S08 and emptied the queue.

**Evidence (logs):**
- `2026-09-20-3.log.gz`: `released on packet limit (0.0 blocks, 78 → 368 → 1221 → 293 packets)`
  — the queue kept growing.
- `2026-09-22-2.log.gz 20:47:59`: Blink released → 20:48:00 `LAGBACK x6 … BLINKx10`
  → Blink OFF. It was switched off by a server correction, not by the drain finishing.
- Confirmed with `javap` on the installed jar: `sendPacketNoEvent` calls
  `func_179288_a`, and the refmap hooks `sendPacket2` on that same method.

**Fix:** `BlinkManager.release(Packet)` — sets a `releasing` flag while sending, and
`offerPacket` does not take a packet while it is set. LagManager still sees the packet (the combined behaviour is unchanged).

> Note: after the fix, `release-per-tick = 2` means "really send 2 C03 a tick while
> 1 comes in", a net drain of 1 a tick. That still breaks the law of ENGINEERING-NOTES §1
> (two position packets in one tick); it now just "ends". To follow §1 it should
> "drop the path and send only the end point". 📝 For the owner to decide.

### 2. ✅ TimerRange had no `isEnabled()` check at all
`onTick`, `onAttack`, `onPacket` and `onRender3D` all ran while it was off:
- In the default MODERN mode: walking forward and looking at a nearby player for a while **pulled the timer to 1.5x with the module off**.
- `shouldResetTimer()` kept setting the timer back to 1, overriding Timer / Scaffold.
- With the `blink` option on, it intercepted received packets while off.

**Fix:** `isEnabled()` added to all four handlers.

### 3. ✅ Ambience kept controlling the world time while off
While off it still cancelled `S03PacketTimeUpdate` and set the time to the `Time` value (default 0) every frame.

**Fix:** `isEnabled()` added to all three handlers.

## 🟠 High

### 4. ✅ KillAura's smooth-back skipped its clean-up
With LB rotations (rotations==4) + `smoothBack`, `onDisabled()` called `setEnabled(true)`
and then `return`ed, skipping:
- `setBlinkState(false, AUTO_BLOCK)` → movement packets stayed held for the whole turn back;
- the `isBlocking` / `fakeBlockState` reset;
- a pending `blinkReset` → blink was switched back on after the module was off.

**Fix:** the clean-up moved before the smooth-back branch, and `blinkReset` is cleared.

📝 Not fixed: during smooth-back `isEnabled()` is true, so Panic reports "stopped"
while KillAura is in fact still on for a few ticks. Quitting the game at that moment saves it as on in the config.

### 5. ✅ KillAura on in the config → NPE at start-up → the config only half loaded
`Config.load()` calls `setEnabled(true)` while the game is starting (no player yet);
`KillAura.onEnabled()` used `mc.thePlayer.rotationYaw` → NPE,
caught by the outermost `catch (Exception)` → **the loop stopped, and every module after it kept its defaults**.

**Fix:**
- `Config.load()`: each module's `setEnabled` in its own try/catch, written to the log.
- A null check in `KillAura.onEnabled()` (`onTick` takes the rotation again once there is a player).
- The same null check in `Fly.onDisabled()`.

### 6. ✅ FakeLag dropped the teleport confirmation (confidence: medium)
S08 arrives (netty thread) → `flushRequested = true` → the main thread handles the S08 and answers with a C06
→ C06 is a C03 subclass, so it is held → in POST of the same tick `discardStalePositions()`
drops it along with the old positions.

**Fix:** while `flushRequested`, a C06 drops the old positions at once and is sent straight away.

### 7. 📝 LagManager holds `C0FPacketConfirmTransaction`
`LagManager.handlePacket` neither excludes C0F nor checks the thread. This conflicts with NOTES §2
"Never delay C0F". LagRange does work in practice and has not been kicked, so it was not changed.
**Suggestion:** use FlagDetector or ServerFingerprint to see whether there are pong-related
disconnects with LagRange on, then decide.

## Round two: the two symptoms the owner reported

### "Blink rubber-bands back"
The main cause is #1. The drain never sent the path, so the server stayed at the anchor
until a server correction (S08) ended the round → the client is pulled back to the anchor = rubber-banding.
The log's `released → LAGBACK … BLINKx10 → OFF` is exactly that order.

Two more paths that cause it:
- **Switching Scaffold off dumped Blink's queue**: `Scaffold.onDisabled()` called
  `setBlinkState(false, BLINK)` whether or not Scaffold itself was blinking.
  ✅ Changed to `BlinkModules.SCAFFOLD`.
- 📝 **Switching Blink off by its key** still sends the whole queue in one tick (NOTES §1). With a small drift
  (1–3 blocks) the server usually accepts it; `max-drift` is still the real lever.

Side effect: Scaffold's safe-stuck used to be recorded in the ActionLedger under the name `BLINK`,
so **part of the `BLINKx` in old flag files is really Scaffold**.

### "FakeLag just gets stuck and cannot move"
Server behaviour confirmed from the decompiled 1.8.9 `NetHandlerPlayServer`:

1. When the server teleports the player (`setPlayerLocation`) it sets `hasMoved = false`.
2. While `hasMoved == false`, **the server ignores every movement packet** until one arrives within
   0.5 blocks of the teleport point (`d3 < 0.25`).
3. While `hasMoved == false`, **every block placement is refused**
   (`processPlayerBlockPlacement`: `if (this.hasMoved && …)`).

A vanilla client answers an S08 at once with a C06 exactly at the teleport point;
that is the packet that ends `hasMoved == false`. FakeLag used to hold that packet and then drop it (#6),
so the server stayed in the "ignore your movement" state = unable to move.

**Evidence:** `flags-20260920-222005.txt` 22:20:14, 5 REJECTs in a row,
the nearest opponent 18–20 blocks away (`body 18.54 … 20.54`), all `FakeLagx106–110`.
Nobody nearby was in the way, yet placements kept being refused — point 3.
There are also chains like `LAGBACK x21 in 0.3s` and `x15 in 1.55s`, matching NOTES §2
"corrections amplify themselves".

✅ The fix for #6 (send the C06 straight away) got one more piece in round two: `flushRequested`
is cleared once it is handled, so the tick does not drop the new positions after the C06 a second time.

**Confidence:** the mechanism itself is certain (server source), but whether it is the *only* reason
FakeLag got stuck needs testing in game. NOTES §5 marks FakeLag as abandoned;
one test game shows whether it is usable now.

### Test result (2026-09-23 19:15, BedFight, `flags-20260923-191559.txt`)
Settings: DYNAMIC, delay 200, release-on-attack on, max-held 40, ping 180–220 ms.

- 31 corrections in 9 seconds, **all 7 entries 1–4 t after hitting someone or 1–7 t after knockback**, none before the game started.
- The largest: `LAGBACK x13 in 0.6s`. Earlier games had `x21 in 1.0s` and `x15 in 1.55s`, about the same,
  so it was not caused by this change.
- Neither `TIMER-ORPHAN` nor `DRAIN-STALL` fired.
- The symptom changed from "stuck, cannot move" to "flagged all the time", but the game was too short to confirm the stuck part is fully fixed.

**Conclusion:** the same reason NOTES §5 gives for abandoning FakeLag. Both triggers are in the design itself:
1. Positions still held after knockback → the server never sees the player move with the knockback → pulled back.
2. `release-on-attack` squeezes the held positions into one send → breaks §1.

The owner has switched FakeLag off; it stays off.

### Round three: a `LIQUID` mode after LiquidBounce
Read LiquidBounce's legacy `combat/FakeLag.kt` (1.8.9) and the nextgen
`ModuleFakeLag.kt`. The biggest difference: **LiquidBounce only holds while closing in on an enemy,
releases everything the moment the fight starts, and then does not hold for a cool-down**; our DYNAMIC did the opposite,
holding mostly during the fight.

New mode `LIQUID` (the original three modes are untouched, configs unaffected):

| Condition | Behaviour | Source |
|---|---|---|
| Enemy within `melee-distance` (3.5) of the server-side position | Release everything and start the recoil | legacy MinAllowedDistToEnemy |
| The server-side position is closer to the enemy than the real one (backing off) | Do not hold | nextgen |
| Own S12 knockback, explosion knockback, S06 health loss | Release everything in order at once (scheduled on the client thread) + recoil | both |
| Attacking (`release-on-attack`) | The attack goes out at once, what was held before it is released in order + recoil | legacy BlinkOnAction |
| Placing, digging, changing the held item, toggling sprint | Release in order + recoil | both |
| Not moving, using an item, a screen open, in water, hurt, singleplayer | Do not hold (no recoil) | legacy / nextgen |
| S08 | **Keep our way**: drop the old positions, send the C06 straight away | Deliberately not copied (legacy sends the old positions, breaking §2) |

New settings: `melee-distance` (3.5), `recoil-time` (750 ms), shown only in LIQUID mode.
Releasing means "send everything in order" (as LiquidBounce does), **not** squeezing to the last position.
Several positions in one tick still break §1, but the recoil makes it rare.

**Suggested test settings:** `mode LIQUID`, `delay` 200 to start (LiquidBounce's default 550 is for low latency),
`range` 8, `melee-distance` 3.5, `recoil-time` 750.
**What to watch:** whether flags still cluster "1 t after hitting / after knockback". If LIQUID works,
flags during fights should drop a lot, and appear instead at the first release when closing in.

## Suggestions for FlagDetector (so this kind of bug reports itself next time)

> Round two implemented the first two; see the previous section.

**Not implemented yet, worth considering:** `TELEPORT-UNANSWERED`: within N ticks of an S08,
no C06 actually went on the wire (watched at the mixin's "really sent" layer, not via PacketEvent,
because PacketEvent fires before a holder intercepts). That would verify the FakeLag fix directly.

Two kinds of this round's bugs could have been caught by FlagDetector but were not being watched:

1. **"A switched-off module doing things":** check `timer.timerSpeed != 1.0` every tick
   while Timer / TimerRange / Scaffold are all off → record a `TIMER-ORPHAN`.
   That catches #2 directly.
2. **"A queue that only grows":** Blink in the `releasing` state and
   `blinkedPackets.size()` has not shrunk for N ticks → record a `DRAIN-STALL`.
   That catches #1 directly (the 1221 packets of 09-20).
3. Part of why attributions like `BLINKx10` were so large: every time the drain took a packet back,
   `ActionLedger` recorded another `held-send`. **With #1 fixed, BLINK's numbers should drop clearly**,
   which can serve as proof of the fix.

## Round six (2026-09-24 evening): FlagDetector counted the start-of-game teleport as a LAGBACK

**Evidence**: in the logs of 09-23 and 09-24 there were 6 LAGBACKs "standing still, horizontal only", all 2–3 seconds after Pika's `Game starts in 1...`. That is the server moving players to their spawn (0.4–7.6 blocks, no S07 before it), not the anticheat pulling anyone back. The distance was under `teleport-distance` (8 blocks), so it was counted as a violation and fed to the rate, the Brain and Adaptive.

**Fix**: a new `RELOCATE`. A setback always returns to a position the client itself sent; if the correction's target is more than 0.3 blocks from every position of the last 10 seconds (200 ticks), it is the server placing the player. Shown in chat and the log file (dark aqua), counted on its own, not a violation, and it opens the 20-tick grace after a teleport. The position history grew from 64 to 200 ticks.

**Owner's addition (recorded in NOTES §2)**: at high latency, blocking a path is often refused because by the time the server registers the block an enemy is already standing there. But the 6 REJECTs at 09-24 19:43 had the nearest opponent over 6.4 blocks away, or no other player in the arena (the opponent had just fallen into the void), so that is not the cause; the cause is still unknown.

### Same round: FakeLag hold log

After a whole game of LIQUID (range 8, delay 200) there was no way to tell whether it ever held a packet: FlagDetector never named it, and the owner never saw a number in the suffix. A new `log` setting (OFF / FILE / CHAT+FILE, default CHAT+FILE, not in LATENCY mode):

- Each hold, once emptied, writes a `HOLD` line: how many packets, how long, the most queued at once, the opponent and distance (start → end), and what released it.
- Each engagement (ended when the opponent has been out of range for 3 seconds) writes an `ENGAGE` line to the file: seconds the opponent was in range, how many of those ticks allowed holding, how many holds, and which condition blocked the rest (sorted by ticks).
- Log file: `config/Myau/fakelag-<time>.txt`.

The hold decision was not changed. LIQUID now looks for a target whether or not the conditions are met, but only uses it when they are, so the result is the same as before.
